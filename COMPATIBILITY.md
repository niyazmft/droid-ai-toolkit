# Compatibility — Tested Versions

The tools this toolkit installs are written for regular Linux servers and change
often. Each upstream release can break an Android-specific fix. This page says
which versions the toolkit was actually verified against, and how to tell us
when your version behaves differently.

## What "tested" means

It means exactly this: on the environments listed below, that tool version
installed, started, and passed the toolkit's checks. It does **not** mean the
toolkit blocks other versions. You can install anything; you are simply told
whether it has been verified yet.

Environments are described by **class — architecture, Android version, RAM band —
not by phone model**. A model name tells you nothing about whether your phone is
covered; the class is what you can map your own device onto. (Model names do
appear in user reports, which is where they are useful.)

Verification currently covers two devices. If your phone falls outside the
classes below, your report is how the list grows.

## If your version differs from the tested one

You are not broken and nothing is blocked. You are simply on a version nobody has
verified yet. Two outcomes are both useful to us:

- **It worked.** Report it, and the version becomes tested for everyone.
- **It broke.** Report it, and we fix the script — the report usually tells us
  which step failed and where.

The toolkit prints a reminder with the report link after an install, and shows
the same table under **Main Menu → [C] Tested**.

## Reporting a result

Use **Main Menu → [C] Tested → Report a result**. It prints a block containing
your toolkit version, device model, architecture, Android version, memory,
storage, the tool and its version, and the tail of the install log.

Copy that block into a new issue:

- [Compatibility report](https://github.com/niyazmft/droid-ai-toolkit/issues/new?template=compatibility_report.yml)

Please include the whole block. The device details and the log tail are what make
a report diagnosable instead of a guess — most reports turn out to be
self-explanatory once they are attached.

## Known issues by version

These are problems already diagnosed. If you hit one, you do not need to report
it again — but say so if a newer version fixed it.

### OpenClaw 2026.9.x on Android

- **Legacy state blocks the gateway.** 2026.9.x gates gateway startup behind
  migrations that upstream normally applies with `openclaw doctor --fix`. That
  command cannot run on Android, so the toolkit applies the migrations directly
  during repair and update. Do not run `openclaw doctor --fix` on Android.
- **Channels crash-loop after migration.** `[default] channel exited: Legacy exec
  approvals exist ...` means the exec-approvals stage did not commit. Re-run
  **AGENTS → OpenClaw → [R] Repair**.
- **Hardlinked transcripts are rejected.** Android blocks hardlinks, so the
  migration patch publishes archived transcripts by copy instead. Applies
  automatically.
- **`cron run cannot acquire a durable fence`.** The process-identity helpers are
  gated on `process.platform === "linux"`, and Termux reports `"android"`. The
  patch accepts both. If you still see it, the patch did not match your build —
  please report.

#### `openclaw doctor --fix` cannot run here — what to use instead

It fails **by design**: its first step takes *maintenance ownership* of the
gateway by stopping and restarting it through a system service manager. Android
has neither systemd nor launchd, so ownership can never be verified — and it can
hang if the gateway is still running. Decline it if an in-chat agent offers to
run it.

That does not leave a functionality gap. Every state-changing repair the doctor
performs has an equivalent that works here:

| Doctor repair | What to use instead |
| :--- | :--- |
| Workspace / session / exec-approvals migration | Automatic — **AGENTS → OpenClaw → [R] Repair** |
| Database schema migrations | Automatic — the gateway applies them at startup |
| Config normalization | Automatic — gateway at load; the installer's config step |
| Session SQLite repair or compact | `openclaw doctor --session-sqlite dry-run\|import\|compact` |
| State SQLite compact | `openclaw doctor --state-sqlite` |
| Advisory health notes | Cosmetic — no action needed |

The `--session-sqlite` and `--state-sqlite` subcommands are handled by the CLI
*before* the broken maintenance step, so they run fine on Android. If a future
release adds a repair this toolkit does not cover yet, prefer its dedicated
subcommand over the full `--fix`.

### After any toolkit update

- **The heap cap can be reset.** An update can restore the default Node memory
  formula, after which the Android low-memory killer silently kills the gateway
  a minute or two after it becomes ready. Check the PM2 environment
  (`pm2 env <id> | grep NODE_OPTIONS`) and re-apply your device's cap.
- **Plugins can be left disabled.** The installer no longer overwrites a plugin
  state you chose, but confirm your plugins are enabled after a version jump:
  `openclaw plugins enable <plugin-id>`.
- **Stale credential profiles shadow the right one.** A leftover provider profile
  (for example `ollama:default` alongside `ollama-cloud:default`) can shadow the
  working credentials and produce `401 Unauthorized`, which then trips the
  restart-loop breaker and suppresses channel autostart. Remove the stale profile
  and start channels by hand if needed:

  ```bash
  openclaw gateway call channels.start --params '{"channel":"telegram"}'
  ```

### 32-bit devices (`armv8l` / `armv7l`)

- **Hermes and Nanobot are not supported.** Their dependency chain requires Rust
  builds that reject those architectures. The toolkit skips them with an
  explanation instead of failing mid-install.
- **Prebuilt Python wheels may not exist.** Anything needing compilation can take
  30–90 minutes or fail. The toolkit caches built wheels under
  `~/.hermes/wheel-cache` so a reinstall does not repeat the work.

## Coverage honesty

This list is only as good as the reports behind it. As of the last update above,
verification covers two devices and nothing else — no emulator run, no other
Android version, no other memory class. If your device is not represented and
something works, that is worth reporting too: it is the cheapest way to widen the
tested set.
